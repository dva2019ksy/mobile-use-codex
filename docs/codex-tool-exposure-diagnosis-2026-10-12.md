# Codex 本机监控工具缺失诊断

检查日期：2026-10-12。初始诊断未修改本机 Codex 配置，也未删除或卸载插件、市场源；后续本地安装验证临时将该市场指向本地源码，避免未发布修复被 Git 来源的旧版本覆盖。

## 结论

故障已定位到 Codex 将已安装插件的 MCP 工具暴露给模型的环节。监控服务返回的目录完整，设备采集正常，但模型运行时缺少打开监控所需的工具。

同一插件包含 `mobile-control` 和 `mobile-use-codex` 两个 MCP 服务。0.2.1 保留完整上游工具定义，将服务公共流程集中维护在插件自带的 skill 中，不再通过初始化说明重复附加到每个工具。正常插件加载时完整暴露 33 个操作工具和 7 个监控工具，不需要调整用户 MCP 配置。

减少操作工具定义后，监控工具恢复的数量与被移除工具的定义大小相关。这支持“同一插件的工具定义触发大小预算，尾部定义被裁剪”的解释；尚未确认客户端内部具体阈值和实现位置，不应将其描述为固定的工具数量上限。

## 环境

- 桌面程序：26.1007.30912。
- 内置 CLI：0.162.0-alpha.17.2。
- mobile-use-codex：0.2.0，安装 revision `00ef6553f76fffa73b03431ddd223e0515a36a08`。
- 模型工具模式：code mode，启用 `features.code_mode_host`。

## 已验证的事实

监控 MCP 的 `tools/list` 返回 9 个工具。其中 `read_frame`、`release_frame_viewer` 明确标记为仅供面板调用，模型应看到另外 7 个：

`begin_operation`、`close_monitor`、`end_operation`、`list_devices`、`monitor_status`、`open_monitor`、`renew_operation`。

实际会话的 `ALL_TOOLS` 只有 `begin_operation`、`close_monitor`。因此助手可以操作设备，却无法正常调用 `open_monitor` 打开侧栏画面。

采集烟测通过：HTTP 收到 45 帧，MCP 收到 30 帧，约 26.3 fps；设备操作目录有 33 个工具，读取设备画面成功，结束后采集停止。此项验证覆盖采集和传输，不代表桌面侧栏组件已完成实际渲染验证。

用户配置和插件清单未发现相关工具的 enabled/disabled 过滤名单。

## 对照实验

使用同一台机器、同一 CLI 和同一份监控服务程序。独立诊断进程通过临时本地 Responses 模拟服务执行只读取 `ALL_TOOLS` 的代码；未调用真实模型，未操作设备。配置差异仅通过诊断进程的命令行覆盖传入。

| 条件                                                                    | 设备操作工具 |     模型可见监控工具 |
| ----------------------------------------------------------------------- | -----------: | -------------------: |
| 原始完整配置，两个服务归属同一插件                                      |           33 |                    2 |
| 关闭其他应用工具，保留该插件                                            |           33 |                    2 |
| 同时新增一份普通 MCP 监控服务                                           |           33 | 原插件 2，普通 MCP 7 |
| 关闭插件的操作服务                                                      |            0 |                    7 |
| 操作服务仅保留按名称排序的前 32 个工具                                  |           32 |                    3 |
| 操作服务移除较大的 `mobile_allocate_remote_device` 定义                 |           32 |                    5 |
| 操作服务仅保留按名称排序的前 30 个工具                                  |           30 |                    7 |
| 操作服务移除 `mobile_allocate_remote_device` 和 `mobile_batch_commands` |           31 |                    7 |
| 插件仅关闭监控服务，以相同服务名配置普通 MCP 监控                       |           33 |                    7 |
| 保留完整上游工具目录，仅移除控制服务初始化的公共说明                    |           33 |                    7 |

独立普通 MCP 环境再加入 600 个模拟工具、增大其描述总量后，监控仍完整提供 7 个工具。没有证据支持“全局工具数量过多导致此问题”。关闭 tool-suggest 或改变 MCP 延迟加载开关也没有恢复插件内缺失的工具。

## 插件内修复：0.2.1

Codex 会把上游 `mobile-mcp` 的公共说明重复加入每个操作工具的模型描述。原来直接运行上游 CLI，整套说明与监控工具在同一插件内合并后，监控工具只有按名称排序的前两个进入模型运行时。

修复内容：

- 新增 `server/control.mjs`，继续使用上游 server factory 与原始工具执行逻辑。
- 新增 `server/control-transport.mjs`，只移除与 `initialize` 请求对应的响应中的可选字段 `instructions`；工具目录、调用结果、错误及通知均透传。
- 显式设备选择、远程设备费用与释放、元素优先读取、已知步骤批处理及 URL 限制等公共流程集中维护在 `skills/mobile-monitor/SKILL.md`，使用插件执行设备任务时加载。
- 保留全部 33 个操作工具的完整上游定义，包括原始描述、设备参数说明、批处理工具名列表、参数约束、注解、截图及工具结果。监控服务和 MCP 清单不变。
- 新增完整目录契约测试及上游公共规则变化校验；新增 `npm run test:codex-tools`，使用真实 Codex CLI 检查模型运行时的 `ALL_TOOLS`。不设置说明字符数或目录体积门槛。
- 版本更新至 0.2.1。

验证结果：

- 独立 Codex 插件安装目录中，两个服务均归属 `mobile-use-codex@mobile-use`，原始目录为 33 + 9；模型运行时完整暴露 33 + 7。
- 负对照：将临时插件恢复为旧启动方式，新回归测试稳定失败，检出 `open_monitor` 等工具缺失。
- `npm run check`：格式、lint 与 12 项测试通过，包含完整上游目录契约、初始化响应关联、模拟设备操作、截图和采集清理。
- 此前的 iPad 只读烟测：读取设备页面成功，HTTP 45 帧、MCP 30 帧、约 24.6 fps，结束操作后停止采集。最终方案重新验证模拟设备采集、工具目录与真实 Codex 工具暴露；不将此前烟测等同于新方案的真机 UI 验证。
- 本机安装 0.2.1 并重启后，当前对话实际暴露全部 33 个操作工具和 7 个监控工具；操作工具的描述不再带有重复公共说明。
- 原生侧栏验证通过：调用 `open_monitor` 后，Codex MCP Apps 侧栏显示真实 iPad 设置页面，采集与显示帧率均约 24 fps。测试期间共采集 977 帧；调用 `end_operation` 后，状态为 `idle`、活动操作为 0，侧栏显示“操作已结束 · 采集已停止”。此项实际观察覆盖原生 widget 渲染，而非仅验证 HTTP 诊断页或工具成功返回。

## 本地安装与市场来源

仅在安装命令中临时覆盖 Git 市场来源，会使本地安装的未发布版本在客户端重启同步时被 Git 来源的旧版本覆盖。本地验证应临时将该市场配置为本地源码，并重启加载；修复推送到 Git 来源后，再恢复 Git 市场并从该来源安装。该安装来源问题与工具说明重复附加是两个独立问题。

此前独立加载监控服务的实验仅用于定位问题，未应用到用户配置，也不作为插件修复方案。

市场页的 `mobile-use` 是该插件的安装与升级来源，本次故障不需要通过删除市场源解决。
